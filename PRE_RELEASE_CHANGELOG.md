## Bug Fixes

- **Nullish request url:** A request with a `null` or `undefined` url on a built-in adapter, whether selected by name or passed as a function such as `axios.getAdapter('fetch')`, now rejects with `AxiosError` and `ERR_INVALID_URL` before anything is sent. Since v1.18.1, adding `params` turned such a url into a query-only url like `?foo=bar`, which browsers resolve against the current page, so `axios.get(null, { params })` sent a request to the page itself. Without params, XHR requested `./null` or `./undefined`, and the Node HTTP adapter threw a native `TypeError`; both now reject with the same `AxiosError`. A `baseURL`, or a `socketPath` on the Node HTTP adapter, still supplies the destination; an empty-string url is still a valid relative url; custom adapters are not checked; and `axios.getUri()` still returns query-only urls. No public API or type changes. (**[#11237](https://github.com/axios/axios/pull/11237)**, closes **[#11160](https://github.com/axios/axios/issues/11160)**)
- **Response duration clock:** `response.duration` is now measured with the monotonic `performance.now()` instead of `Date.now()`, falling back to `Date.now()` only in runtimes without `performance.now()`. Since v1.21.0, axios read `Date.now()` on every request, which broke Next.js production builds that use Cache Components (`cacheComponents: true`) because Next.js rejects reading the current time while prerendering; `performance.now()` is the timing API Next.js allows for this. The monotonic clock also stops system clock adjustments from skewing the value. `duration` is rounded to whole milliseconds, so it stays an integer as in v1.21.0, and it is still clamped at `0`. No public API or type changes; the `duration` declaration comments in `index.d.ts` and `index.d.cts` now name the clock. ([#11407](https://github.com/axios/axios/issues/11407))
- **`getAdapter` typings:** `getAdapter(adapters, config?)` in `index.d.ts` and `index.d.cts` now accepts the optional request config that the runtime already forwards to adapter getters, so `getAdapter('fetch', { env: { fetch } })` type-checks without a cast. A JSDoc comment on the parameter notes that the built-in `fetch` adapter reads `env.fetch`, `env.Request`, and `env.Response` from it and that other fields are not applied. Type-only; additive and backwards compatible, no runtime change. ([#11403](https://github.com/axios/axios/issues/11403), [#11404](https://github.com/axios/axios/pull/11404))
- **Header encoding shortcuts:** The documented `Content-Encoding` shortcuts (`setContentEncoding`, `getContentEncoding`, `hasContentEncoding`) now exist at runtime; previously `getContentEncoding()` threw `TypeError` because `AxiosHeaders` only registered the `Accept-Encoding` accessor. The `Accept-Encoding` trio that the runtime already provided is now declared in `index.d.ts` and `index.d.cts`. `getContentEncoding` and `getAcceptEncoding` are typed to match `AxiosHeaders#get`: `AxiosHeaders.parseParameters` returns `AxiosHeaderParameters`, a `RegExp` returns `RegExpExecArray | null`, and no argument, `true`, or another parser function returns `AxiosHeaderValue`. The type changes are compile-time corrections, not purely additive: `getContentEncoding()` was previously declared to return `RegExpExecArray | null` and to accept string matchers, which throw `parser must be boolean|regexp|function` at runtime, and `getAcceptEncoding()` previously resolved to `any` through the `AxiosHeaders` index signature. TypeScript callers that relied on those declarations may need to narrow the result or pass a supported parser. No change to how existing headers are read or written at runtime; the matching README and docs-site shortcut-list updates are recorded in `PRE_RELEASE_DOCS.md` for release preparation. ([#11432](https://github.com/axios/axios/issues/11432))

- **`redact`, size-limit and `formToJSON` clarifications:** Documented three existing behaviours in the README and in the English, Spanish, French, and Chinese docs site. For `redact`, the request config, error handling and security pages now say that objects other than plain objects and `AxiosHeaders` that have a `toJSON()` method, such as `URL` objects and class instances that define `toJSON()`, are serialized without being scanned, that credentials inside URL strings are not matched because `redact` matches key names, and that listing the parent key, such as `auth` or `proxy`, masks the whole value. The security page now says that `maxContentLength` and `maxBodyLength` are enforced by the Node.js HTTP adapter, by the fetch adapter when it can determine the size or track the stream, and not by the XHR adapter, and recommends `adapter: 'fetch'` for capping response size in browsers; the `maxContentLength` request config entry notes the same. The "Converting FormData to JSON" sections now explain that colliding field names are combined: a repeated name becomes an array, and when the same name is also used as a parent path the result depends on field order and can lose the plain value, so applications should validate the object `formToJSON()` returns rather than the original `FormData` entries. Documentation only; no runtime, public API, or type compatibility changes. ([#11419](https://github.com/axios/axios/pull/11419))

- **Error code tables:** Added the missing `ECONNREFUSED` row to the error code tables in the README and in the English, Spanish, French, and Chinese error-handling guides, and added the missing `ERR_FORM_DATA_DEPTH_EXCEEDED` row to the README table. That row and the guides also note that parsing FormData into JSON, by `axios.formToJSON()` or when a spec-compliant `FormData` (one with an `entries()` method) or HTML form is sent with `Content-Type: application/json`, has a fixed limit of 100 levels that `maxDepth` does not change, and the "Converting FormData to JSON" sections now say the same. This is documentation only, with no runtime, public API, or type compatibility change. ([#11429](https://github.com/axios/axios/pull/11429), [#11430](https://github.com/axios/axios/pull/11430))
- **Request config and header docs:** Corrected descriptions in the README and in the English, Spanish, French, and Chinese docs that did not match the code. `transformRequest` runs for every request method and its last function may also return a `Blob` or `File`, transform functions also receive the headers (and the status code for responses), `responseType` and `Content-Type` have no default value (`Content-Type` is derived from the request data for the types the default request transform handles, with an `application/x-www-form-urlencoded` fallback for `post`, `put` and `patch`), `AxiosHeaders#get()` takes an optional parser and returns the raw value when none is passed, and `AxiosHeaders#normalize()` runs before each transformer and once after them, not after each interceptor. Documentation-only; no runtime or type changes. ([#11389](https://github.com/axios/axios/pull/11389))

## Maintenance

- **Config validation guidance:** Narrowed the `validator` rule in `AGENTS.md` and `.github/copilot-instructions.md` to type and shape checks on config options in `Axios#request`. `validator.assertOptions` runs there before request interceptors, checks only the options listed in each schema, and skips options whose value is `undefined`, so a check that needs the final config after interceptors, an option that may be `undefined`, or the selected adapter cannot use it. The guidance now says those checks belong on the request path, such as `dispatchRequest` or the adapter, not in shared helpers that `axios.getUri()` also uses, and that they throw `AxiosError` with a specific code. Contributor guidance only; no runtime, public API, or type changes. ([#11439](https://github.com/axios/axios/pull/11439))
- **`no_proxy` matching test coverage:** Added unit tests for `shouldBypassProxy` covering internationalized domain name entries (Unicode and Punycode on either side, case, wildcard and leading-dot prefixes, explicit ports, and entries that cannot be converted to ASCII), empty and port-only entries, malformed CIDR bases (unbalanced or misplaced brackets, bracketed IPv4, trailing dots, and IPv4-mapped IPv6 ranges shorter than the /96 mapping prefix), malformed IPv4 entries, and port-qualified entries for protocols with and without a default port. The new tests document the existing fail-closed behavior; runtime behavior, public APIs, and types are unchanged. ([#11431](https://github.com/axios/axios/pull/11431))
- **Cancellation lifecycle regression coverage:** Added Node HTTP/Fetch and browser XHR tests for cancellation inside asynchronous request interceptors and successful reuse of an Axios instance after an in-flight cancellation, using AbortSignal, CancelToken, and both together. Added deterministic signal-composition tests for timeout/cancellation precedence and subscription cleanup. Runtime behavior, public APIs, and types are unchanged.

- **Development dependency refresh:** Raised the `package.json` ranges for the development dependencies to the versions in the lockfile, and refreshed the lockfile using only releases at least seven days old, matching the Dependabot cooldown. Vitest and its browser packages move from 4.1 to 5.0, and TypeScript from 5.9 to 7.0. TypeScript 7 at the root is only used by editors; the module type tests keep their pinned TypeScript 4.9 and 5.9. Babel 8 is not adopted because `@rollup/plugin-babel` still requires `@babel/core` 7. `https-proxy-agent` stays on 5.x because later majors need Node.js 20 or newer and the CJS smoke tests still run on Node.js 12. The runtime dependency ranges are unchanged: `follow-redirects`, `form-data`, and `proxy-from-env` are already on their latest versions. The browser UMD bundle (`dist/axios.js` and `dist/axios.min.js`) changes only in Babel's `_toPrimitive` helper, which now checks that `Symbol` exists before using it; the ESM, CJS, and Node.js bundles are byte-identical. No runtime, public API, or type compatibility changes. ([#11426](https://github.com/axios/axios/pull/11426))

- **follow-redirects security update:** Raised the `follow-redirects` dependency range from `^1.16.0` to `^1.16.2` and updated the lockfile to 1.16.2, which fixes [CVE-2026-116689](https://github.com/advisories/GHSA-mrwp-f3q8-3g9p) (cross-realm `sensitiveHeaders` arrays are discarded and custom credentials can follow redirects). Raising the range floor stops installs from resolving the vulnerable 1.16.0 and 1.16.1 releases. No axios runtime, public API, or type compatibility changes. ([#11409](https://github.com/axios/axios/issues/11409), [#11410](https://github.com/axios/axios/pull/11410))
- **CI runners:** Switched GitHub Actions jobs from GitHub-hosted `ubuntu-latest` runners to the `namespace-profile-axios` Namespace runner profile. The npm publish job stays on `ubuntu-latest` because npm provenance and trusted publishing require GitHub-hosted runners. CI only; no runtime, public API, or type compatibility changes.
